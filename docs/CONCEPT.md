# design.wolf.ua — концепция (итог обсуждения)

Версия 2.1, 2026-11-08. Собрано из обсуждения 06–08.11. Первый черновик сохранён в `design-wolf-ua-concept-v1.md`.
Пометка ❓ — ещё не решено, ⚠️ — проверить до разработки.

## 1. Что это

Фриланс-сайт для дизайна под печать в экосистеме wolf.ua. Клиент заполняет бриф, дизайнеры присылают предложения с ценой. Клиент выбирает дизайнера, они вместе работают в чате на превью, дизайнер загружает макеты, а клиент нажимает «Купую». Купленные макеты попадают в облако клиента на wolf.ua, и из них сразу делается заказ печати.

Среди дизайнеров есть и «наши». Менеджер, получив заказ по телефону, заходит под клиентом и делает всё то же самое.

Название: «Мастерская дизайна» (на сайте — «Майстерня дизайну»).

## 2. Принятые решения

| Тема | Решение |
|---|---|
| Продавец | Всегда wolf.ua, одна компания. Дизайнер — исполнитель |
| Изоляция | Отдельный проект, код wolf.ua не меняем. Если не взлетит — выключаем, ничего не выпиливая. Единственная правка в wolf.ua — куки `_am` и `wolfid` на поддомены (раздел 3) |
| Кошелёк | Один: `customers.inv_sum`. Каждое движение — строка в `transaction` (`orderstatus=COMPLETE`, `payment_done` ±). История объясняет происхождение денег |
| Комиссия | Настраиваемая цифра (env или окно в админке), будут менять. Одна для всех каналов |
| Цена | Только в поле предложения, не в переписке |
| Оплата | В конце: клиент нажимает «Купую», когда загружен хотя бы один макет |
| Выполнено | = клиент купил. Несогласие — через жалобу |
| Брифы | Видят только дизайнеры |
| Дизайнеры | Кто угодно, по заявке с портфолио. Старт с рейтинга 5★ |
| Вывод денег дизайнером | Существующий ручной механизм через менеджера. Гонорар не держим: вывод и так долгий |
| Уведомления | api2 `sms/add`, дальше система сама выбирает Viber, Telegram или корпоративный чат |
| Бухгалтерия | Не трогаем (`is_1c` — флаг передачи счёта в 1С, `inv_sum_bn` — брошенная колонка) |
| Старый design.wolf.ua | Брошен. База остаётся, сайт архивируем на пару лет, потом удаляем |
| Юрист (договоры, права) | В самом конце |

## 3. Роли и вход

| Роль | Кто | Как входит |
|---|---|---|
| Клиент | Любой клиент wolf.ua | Общий вход через куку `wolfid`, как у calendar. Регистрация и логин на wolf.ua |
| Дизайнер | Клиент wolf.ua с одобренной заявкой | Так же. Профиль дизайнера — в таблицах design |
| Менеджер | Сотрудник | Входит под клиентом существующим механизмом `Customer::autorizationFromAdminka` (кука `_am` — метка менеджера). Кнопки оплаты и подтверждения скрыты, кроме доверенного круга (как на wolf.ua) |
| Админка | Сотрудники | Просмотр всех брифов, заказов и чатов. Доступы определяет админка |

Куратор клиента (`customers.curator_id`) назначается всем принудительно кроном `wolf.ua/cron/work_with_db.php`, в том числе новым клиентам с design.

⚠️ **Вход менеджера на поддомене:**
- Сейчас `wolfid` и `_am` при входе под клиентом ставятся только на хост `wolf.ua`. Решение — ставить обе на весь домен `.wolf.ua`. При этом удалять старые host-only куки, иначе в браузере будут две куки с одним именем.
- design должен расшифровать `_am`, а закрытый ключ зашит в `wolf.ua/helpers/Crypt.php`. Вынести в общий env или проверять через api2 ❓.
- `_am` можно подделать открытым ключом. Поэтому кука годится только чтобы **скрывать** кнопки (как на wolf.ua), но не чтобы **давать** права.

## 4. Продукты дизайна и бриф

- **Продукты** — свой ограниченный справочник design, не связан с товарами wolf.ua: «Візитка», «Буклет», «Брошура на скобі», … Последним идёт «Інше».
- **Бриф продукта** — список «вопрос → примерный ответ» (примерный ответ — плейсхолдер в textarea). Редактируется в админке.
- У «Інше» один вопрос: «Опишіть задачу».
- **Ответы сохраняются вместе с текстом вопроса**, чтобы старые брифы читались после правок опросника.
- Количество вещей («3 види візиток»), ссылки на материалы (любой сервис) — просто текст в ответах. Позиций внутри заказа нет.
- Бюджет клиента не спрашиваем: цену называют дизайнеры.

## 5. Жизнь заказа

**Два режима брифа** (клиент выбирает при создании):

| Режим | Что происходит |
|---|---|
| «Збирати пропозиції» | Бриф видят все дизайнеры. Дизайнер нажимает «Запропонувати себе»: текст, цена «на руки», дата срока → «Надіслати». Клиент видит список: Петя, Вася, Шура |
| «Одразу обрати дизайнера» | Клиент выбирает дизайнера из списка. Дизайнеру приходит «Тебе обрали, береш?». «Так» = та же форма предложения (текст, цена, дата), «Ні» = бриф возвращается клиенту (пригласить другого или переключиться на сбор предложений), куратору уведомление |

Режим «одразу обрати» — основной путь менеджера: зашёл под клиентом, заполнил бриф, выбрал «нашего» дизайнера.

```
бриф ─► опубліковано ─► пропозиції (у кожної — своє листування з клієнтом, тільки текст)
                              ▼ клієнт обрав пропозицію
          робочий простір замовлення (бачать клієнт, обраний дизайнер, менеджер під клієнтом):
                         чат, прев'ю, макети
                              ▼ є ≥1 макет, клієнт тисне «Купую»
               [очікує оплати рахунку] ── оплата з балансу / WayForPay
                              ▼
               куплено = виконано: макети відкриті, в хмарі клієнта
                              │  дизайнер «ще не закінчили» + нова ціна і дата
                              ▼
               доопрацювання ─► «Купую» ще раз, доплата різниці (може бути 0)
Відгалуження: скасовано (до покупки грошей немає — повертати нічого), скарга.
```

- **Предложение:** текст + цена «на руки» (D) + **дата срока** (отдельное поле). Изменение цены или даты = системное сообщение «ціну змінено з X на Y».
- **До выбора** у каждого предложения своя переписка клиента с дизайнером — только текст, загружать файлы некуда (ссылки на сторонние ресурсы не запрещаем). Так бесплатные варианты «на конкурс» не появляются.
- **Выбор:** у выбранного дизайнера появляется рабочее пространство заказа. Его переписка до выбора показывается в начале. Остальные видят «вже обрано іншого дизайнера», их переписки замораживаются только на чтение.
- **«Купую»** активна, только если загружен хотя бы один макет. Перед покупкой клиент видит список макетов (имя, размер), но не файлы.
- **Доработка:** уже купленные макеты остаются у клиента. Новые открываются после повторной покупки.
- **Срок прошёл**, а «Купую» не нажата → уведомление куратору.
- **Жалоба:** кнопка у клиента после покупки. Клиент описывает, что не так, и сообщение уходит куратору клиента и user_id = 1 через `sms/add`. Разбираются вручную.

## 6. Чат

Сообщения живут в двух местах: **переписка по предложению** (до выбора, своя у каждого дизайнера, только текст) и **лента рабочего пространства** (после выбора, одна, с превью). Технически это одна таблица сообщений с привязкой к предложению: лента рабочего пространства = переписка выбранного предложения, продолженная после выбора.

**Сообщение:**
- `offer_id`, `author_id`, `author_role` (клиент / дизайнер / менеджер / система), `text`, `created`;
- необязательный `preview_id` — превью, к которому относится сообщение. Отправка превью тоже сообщение;
- необязательный `reply_to_id` — ответ на конкретное сообщение, показывается цитатой.

**Превью:** заказ, номер v1, v2… сквозной по заказу, `based_on_id` («на основі v2»), файл, `message_id`.

**Правила:**
- **Текст** не правится и не удаляется.
- **Превью** удаляется только мягко: скрытое превью в ленте показывается заглушкой, подпись остаётся.
- **Системные события** — записи в той же ленте с `type=system`: предложение, цена, покупка, жалоба.
- **Обычные файлы** в чат не грузим: ссылки на drive.wolf.ua или любой другой сервис.
- «Прочитано» не делаем: под клиентом может сидеть менеджер.

Отложено: пометки на картинке — отдельным инструментом (простой веб-редактор, на выходе скриншот).

## 7. Файлы

| Тип | Что | Где |
|---|---|---|
| Превью | Картинки для обсуждения, много версий | В ленте рабочего пространства. Файлы — на локальном втором диске `/mnt/work` (своя папка, например `/mnt/work/design/`) |
| Макеты | Готовые файлы: PDF, архив package и т. д. Несколько отдельных загрузок с подписью («Візитка 1», «Візитка 2», «Вихідні.zip»). До покупки закрыты | Архив дизайнов на Storage Box рядом с облаком ❓ (например `/mnt/cloud/design/archive/…`), один экземпляр |
| Купленный макет у клиента | Каждый макет — отдельная запись облака: «Дизайн №N — Візитка 1.pdf» | Облако wolf.ua: симлинк `/mnt/cloud/f/…` → архив + строка `customers_cloud` (`type_id=1`, иначе картинки перекодируются в WebP) |

- **Из облака** клиент сразу делает заказ печати («взяти з хмари» → `status25` копирует файл в заказ → обычная проверка). Ничего не скачивает и не распаковывает.
- **Ссылка для дизайнера** (`order-upload-remote`) — копия страницы загрузки макета без чувствительных данных, с автоматической и ручной (profProv) проверкой. design может сам сгенерировать её для заказа печати клиента: публичный ключ в `cdn.wolf.ua/helpers/Crypt.php` совпадает с wolf.ua. Это дополнительный путь, основной — облако.

⚠️ Проверить:
- **Симлинки на настоящем Storage Box через sshfs** — запись на storage box, с разрешения. Симлинк относительный.
- **Архив дизайнов не удалять** даже после закрытия design, иначе симлинки в облаках станут битыми.
- **Бэкапы облака** — с сохранением симлинков.

⚠️ **Папка превью на `/mnt/work`** — вне путей, которые чистит `wolf.ua/cron/cleaner_folders_work.php` (`web/rip`, `tmp/tmp_uppy`, `virtual_proof`, `source.wolf.ua/disk_files`, `new_constructor/…`, `!trash/…` и др.).

Симлинки на `/mnt/cloud` в wolf.ua уже используются: публичные ссылки на файлы облака — симлинки в `/home/connect/cloud-links/{cf,ci}`, битые удаляет `cron/cleaner_symlink.php`. Цепочка «ссылка → облако → архив дизайнов» должна работать, но это тоже проверить.

❓ Сколько хранить скрытые превью, лимит размера загрузки.

## 8. Деньги

**Цена.** D — сумма дизайнера, k — комиссия, P — цена для клиента. В предложении хранится снимок D, k и P, чтобы изменение настройки не трогало уже сделанные предложения.

**Решено:** дизайнер вводит сумму «на руки» D, клиент видит P = D·(1+k). В форме: «Ви отримаєте 1 000 грн · клієнт побачить 1 200 грн». k называть наценкой (20 грн из 120 — это 16,7% от цены клиента). Округление P ❓.

**Все способы оплаты сводятся к балансу.** Код один, история одинаковая:

| Способ | Как |
|---|---|
| Баланс | Хватает `inv_sum` → списание сразу |
| WayForPay | Отдельный аккаунт design, подключение заново по документации. Колбэк пополняет `inv_sum` (строка в `transaction`), затем то же списание. Колбэк должен быть идемпотентным (WFP повторяет запросы). Мгновенный вывод на карту дизайнеру не нужен |
| Счёт ФОП/ТОВ | Статус «очікує оплати рахунку». Счёт оплачен → баланс пополняется существующим механизмом админки → design видит деньги и проводит покупку |

⚠️ **Счёт (решение — после разговора с бухгалтером).** api2 `payment/create_bill` выставляет счёт только на заказы wolf.ua (`orders`). Для design нужен вариант без заказа (позиция «Послуги дизайну за замовленням №N») — правка в api2, не в wolf.ua. Другой вариант — существующий «предварительный счёт» (`addProductToPreliminaryBill`), проверить.

**Движения:**

| Событие | Клиент | Дизайнер |
|---|---|---|
| Покупка | −P (`[design] Оплата замовлення №…`) | +D (`[design] Гонорар за замовлення №…`) |
| Доплата после доработки | −(P_new − уже оплачено) | +(D_new − уже начислено) |
| Жалоба признана | Решают вручную: возврат — строкой в `transaction` | Решают вручную |

- **Списание и начисление** — одна атомарная операция (транзакция БД, `UPDATE … SET inv_sum = inv_sum - P WHERE id = ? AND inv_sum >= P` + строки в `transaction`). Не делать как в `donateVSUInvoice.php`, где баланс сначала читают, а потом пишут.
- ⚠️ **Вывод дизайнера** (`adminka/pages/fns/designRemoveCash.php`) уменьшает `inv_sum` без строки в `transaction`. Чтобы история сходилась, туда нужно добавить запись — правка в adminka.

## 9. Уведомления

Через api2 `sms/add`. Адресат сотрудника — куратор клиента (`customers.curator_id`), для жалобы ещё user_id = 1.

События для менеджера:
- бриф без предложений сутки;
- дизайнер отказался в режиме «одразу обрати»;
- срок прошёл, а покупки нет;
- (позже: клиент не выбирает предложение, дизайнер молчит, тишина в работе — в первый запуск не делаем);
- жалоба.

В текст всегда включать номер заказа и суть: очередь `n_smser` отсекает повторы по `msg_key`.

**Клиенту и дизайнеру** — тоже через `sms/add`, почту пока не подключаем: новое предложение, «тебе обрали», новое сообщение, макет загружен, покупка.

## 10. Техника и изоляция

- Отдельный проект `/home/connect/design.wolf.ua`, свой vhost. Старый код — в архив.
- Свои таблицы с префиксом `design_` в общей `w2p`. Старые `n_design*` не трогаем.
- **Общие данные:**
  - только чтение — `customers`, `orders`, `orders_files`;
  - запись — `customers.inv_sum` + `transaction` (через одну функцию движения денег), `customers_cloud` + симлинки в `/mnt/cloud`.
- **Если закрываем:** открытые заказы закрыть, vhost выключить. Остаются строки `transaction` с пометкой `[design]`, записи и симлинки в облаках клиентов, архив дизайнов (не удалять).
- При тестах на dev: `/mnt/cloud` там локальная папка, а `/mnt/work2` — настоящий киевский сервер.

## 11. Первый запуск и потом

**Первый запуск:** продукты и брифы (оба режима), предложения, простой список дизайнеров с портфолио (нужен для «одразу обрати»), выбор дизайнера, чат с превью, загрузка макетов, «Купую» (баланс, WayForPay, счёт), облако, жалоба, уведомления менеджеру, заявка дизайнера.

**Потом:**
- каталог дизайнеров с фильтрами;
- отзывы и рейтинг;
- привязка дизайнеров к продуктам;
- пометки на картинке;
- автоматизация вывода денег;
- договоры и права (юрист).
